# CLAUDE.md — Permanent rules for CodeQuest

Read this first in every session, then `PROGRESS.md` (current state) and `ARCHITECTURE.md` (how it fits together).

## What this project is
CodeQuest is a long-term, browser-based educational RPG. Its goal is NOT to teach syntax trivia; it is to take a player from beginner knowledge to **independently solving unfamiliar technical problems**: writing code from a blank file, debugging, working with data and databases, building web apps, using APIs, analyzing information, researching unfamiliar technologies, testing/verifying their work, and creating original projects **without relying on AI to hand them the solution**.

Target skills (eventually): programming fundamentals, Python, SQL/databases, JavaScript, HTML, CSS, data analysis, statistics, R, APIs, Excel, Git/GitHub, debugging, testing, research, problem solving, multi-technology projects.

Baseball is a recurring *theme* and source of examples, never the limit of the curriculum. Examples and challenges must also draw on engineering, software, business, finance, healthcare, manufacturing, research, and other technical fields so skills transfer.

## Project principles (non-negotiable)
1. This repo is the permanent home of CodeQuest. No separate repos/projects per phase.
2. Development is incremental, in phases. Preserve existing functionality unless there is a strong technical reason to change it (and record the reason in PROGRESS.md).
3. Avoid over-engineering. Build what the current phase needs; don't add speculative abstractions.
4. No giant monolithic files. Keep modules small and single-purpose.
5. A future developer (or Claude session) with no conversation history must be able to understand the project from the docs and code.
6. Prefer **real code execution** (tests run against the player's code) over string-matching expected answers.
7. **XP, levels, quests, achievements, and progression are NEVER proof of mastery.** They are pacing/engagement. Mastery is computed only from `EvidenceRecord`s of demonstrated performance, weighted by independence (see `src/learning/mastery.ts`). Never gate "mastered" status on XP or completion counts.
8. Guidance must fade: early content is guided; later content gives blank files, no hints, unfamiliar contexts, and open-ended projects. Using hints/solutions must lower the evidence strength recorded.
9. Curriculum is **data** (`src/content/`), separate from engine code, so content can grow long-term without rewriting systems. The game must not require regenerating curriculum every few days.
10. Do not build the five curriculum phases or bulk placeholder content ahead of the phase that calls for them.

## Educational design rules (learned building Phase 1: keep them)
- Every challenge is verified by **behaviour** (checks on output / variables / function results, plus AST constraints when a construct is the point). Never compare the player's source text to one "right answer". Accept every valid implementation.
- Each challenge needs **hidden edge cases** (boundaries such as `>=` vs `>`, negatives, zero, "the only difference between two wrong ideas") so hard-coding or off-by-one solutions fail. Content tests exist to catch weak checks: add wrong attempts to `solutions.testdata.ts` for any plausible misconception.
- Hints go conceptual → specific → strong, and **never contain the full solution**. Feedback names the *thinking* to do; it must not print the answer. Hidden checks only reveal that a hidden case failed.
- Teach a concept only when the next task needs it. Each lesson: explain → runnable demo (player must run it) → guided practice (learning) → less-guided challenge(s) (challenge mode). Introduce real errors on purpose (debugging is a core skill).
- Use varied real-world contexts (engineering, manufacturing, business, finance, science, data, automation, games); baseball is occasional flavour (content test caps it).
- **Independent mode must not name the language constructs, functions, algorithms, libraries, or steps.** Later phases should make the independent tier more open-ended and add unfamiliar-technology (transfer) problems.
- Be honest in the UI: learning-mode passes are recorded as *guided*, never "independent". Never label XP/level/achievements/quest completion as skill. The shop must never sell answers, hints, or evidence.
- Never use `innerHTML` for content; never `eval` player code on the main thread.

## Educational design rules added in Phase 2 (keep them)
- **Variants, not repeats**: every objective that matters has 2+ variants (`objectiveId`) with the same language/skills/concepts/difficulty and DIFFERENT contexts and data. A retry offers a different problem; failures are never erased (evidence keeps `priorFailures`). Success on a retry is never automatic mastery.
- **Mastery needs variety**: skill requirements ask for independent passes across distinct challenges, objectives AND contexts. `content.test.ts` proves shipped content can satisfy them. Never show a numeric mastery score.
- **Hidden data**: SQL/Python data checks must run on a hidden twin database (`x-b`) or alternate fixture so hard-coded answers fail. Check `sqlSchema`/`sqlPlan`/`sqlState` for design, performance and DML tasks instead of comparing text.
- **Every wrong attempt is a test**: for each challenge add plausible misconceptions to the `solutions*.testdata.ts` files; if a wrong attempt passes, the check is weak: strengthen the check, not the wrong attempt.
- **Docs are practice**: new documentation goes in the Field Manual (`content/reference.ts`) with an executable example; independent challenges may need tools never taught. Never make the Field Manual print a full solution.
- Sandboxes (SQL Sandbox) never write evidence and never touch the game save.

## Educational design rules added in Phase 3 (keep them)
- **Web code is graded in a real browser**, never by comparing source text: structure (DOM/semantics/a11y), computed styles and geometry at several viewport widths, behaviour driven through real events, and timing on a virtual clock. Hidden checks and a hidden API data set (`api: 'b'`) defeat hard-coding. Player HTML/CSS/JS only ever runs in the sandboxed iframe (`allow-scripts`, no `allow-same-origin`); see `docs/WEB_SANDBOX.md`. Never loosen that sandbox or give player code the host page.
- **Independent web tasks** give a brief and, at most, the page skeleton (the ids the checks need). They do not name JavaScript constructs, DOM APIs, `fetch`, `localStorage` or timer functions. Documentation for tools never taught lives in the Field Manual (`content/reference.web.ts`, every entry has a runnable page executed in Chromium by `web.test.ts`).
- **Daily Challenge** (`game/daily*.ts`, `content/daily/`): ONE attempt, NO hints, NO retry, NO solution reveal; rewards (coins, XP, Focus, cosmetics) only on a solve and never affecting mastery; the 12-hour timer is persisted and cannot be gamed by moving the clock back; missing a day costs nothing and there is no streak pressure. Selection is deterministic and explainable (see ARCHITECTURE.md). Dailies are independent-style: no concepts, hidden checks, required lessons that exist.
- **Retention is explained, never scored**: reviews are suggested when a learned skill has been quiet for a week and always say why. Nothing hidden, no numeric score.
- **A wrong attempt that passes is either a weak check or an equivalent solution.** Strengthen the check (or the data, e.g. deliberate boundary rows in the API/SQL data sets) if it is a real misconception; delete the attempt if it is genuinely equivalent.
- The web/API **check helpers** (`h.*`) are part of the content contract: changing `sandboxRuntime.js` can change every check. Re-run `npx vitest run src/content/web` after touching it.

## Educational design rules added in Phase 4 (keep them)
- **Training is a detour, never a step backwards.** When evidence shows a weakness (after a failure, a hinted pass, a weak combination, a quiet skill), the player is offered *training* (`game/training*.ts`): a plan of refresher, example, guided practice and independent problems, sized to the evidence (minor slip: a small refresher; hint used: reinforcement plus a fresh problem plus an independent attempt; serious or major: a longer path). Training NEVER changes lesson progress, quests or unlocked areas, costs no Focus, and always returns the player to the exact place they left (lesson step, boss gate). There is no global failure limit and no lockout timer: training scales with evidence, and repeated failure makes the diagnosis deeper, not harsher.
- **Mastery is never erased.** Evidence is append-only. A later mistake creates a *weakness* (history, with reasons); it never lowers a skill's status. The Skills view shows previous independent performance and recent application trouble side by side. A weakness is resolved only by an independent pass on a DIFFERENT problem (different objective or context), never by a guided/hinted pass or by repeating the same problem.
- **Fresh problems.** Training, boss retries and variants always come from different problems, contexts and data (`pickFresh`). Training draws only from content the player has been taught (plus eligible dailies); a reused problem is a documented last resort when the pool is thin.
- **Diagnosis is evidence, not a guess.** Challenges may carry structured `diagnostics` (primary/supporting/prerequisite skills, named mistakes, which failed check points at which skill; defaults derive from `skillIds`). `game/diagnosis.ts` turns the evidence and the grader's `FailureDetail` into a small, specific weakness with plain-language reasons; combinations (`content/composites.ts`) are first-class.
- **Bosses are unfamiliar, hint-free, one attempt per version** (`content/bosses.ts`, `content/boss/`, `game/boss.ts`). A failed boss is diagnosed and *sealed* until its training is complete, then a NEW version is offered (never the same problem). Boss versions live outside lessons, dailies and the Practice Yard so a player cannot meet them early. A boss win is evidence and rewards, never a mastery mark. Every boss version needs reference solutions and wrong attempts (`content/boss/solutions*.testdata.ts`) and hidden data; where a near-miss must fail, add deliberate boundary rows to a hidden twin database (`works-boss`, `works-edge`, `market-edge`), never to the visible one.
- **The campaign is finite.** The Summit Trial ends it (`campaign.completedAt`). The lesson count is never a ceiling: content grows, the ending stays. Story is data (`content/campaign.ts`).
- **Daily Challenges review old and new together.** Selection (still deterministic and explainable) prefers challenges that combine an older skill with what is being learned now, and challenges that exercise a weak combination, and says so in the reason.
- **Test-only solution files must run under plain Node** (the e2e runner imports them): no imports, only type annotations. Python code in them is written with `String.raw`.
- **Check helpers can leak state between runs.** The Python harness resets logging (handlers, levels, named loggers) before every run so a program that forgets `setLevel` cannot pass because an earlier run set it. Keep the harness's "fresh program" promise when adding standard-library-heavy lessons.

## Educational design rules added in the Phase 4 revision (keep them)
- **Required training is enforced in the game layer, not just the UI.** After a meaningful lesson failure or any failed boss attempt, `requiredTraining(save)` holds `submitChallenge`, `advanceStep`, `completeLesson` and practice until the plan is complete. Never add a second route around it (no retry buttons, no Rest, no "try a fresh problem", no skip) and never let a screen start training on its own: the Mentor has ONE button, "Go to the Training Grounds".
- **Training is a separate place** (`TrainingYard`, area `training-yard`). The lessons area (`training-grounds`, shown as "Programming Hall") must not host training UI.
- **Training content is authored, not replayed** (`content/training/`): a reframing, a different-context example, a prediction, practice, and exactly ONE independent, hint-free proof at the end of a plan (a failed proof adds targeted practice and a NEW proof). Every module/problem needs tests and wrong attempts; test-only solutions run under plain Node.
- **Optional vs required**: lesson/boss sources create required weaknesses; practice, daily and quiet-skill weaknesses are optional and appear only on the Training Board. A hinted pass in a learning-mode exercise is never required.

## Educational design rules added in Phase 5 (keep them)
- **The curriculum is a graph, not a line.** Foundation worlds (Python, SQL, Web, Git, Spreadsheets, R) are open from the first minute and freely switchable; a player may begin in any of them and leave whenever they like. Advanced and cross-world content is gated by **demonstrated competencies**, declared as data (`Skill.prerequisites`, `Lesson.requires`, `Challenge.requires`, area locks) and evaluated in ONE place, `game/graph.ts` (`competencyOf`, `lessonGaps`, `lessonAccess`, `areaGaps`, `challengeEligible`). Never add a second access rule in the UI or a screen, and never hard-code "finish Python first".
- **A gate always explains itself.** Every blocked lesson/area/boss names the exact missing skills (with what level is needed and what the player has), the lesson that teaches each one that is OPEN right now, and what finishing it unlocks (`PrerequisitePanel`, `Locked`). Never show a bare "locked". The Focus gate keeps its own wording ("Not ready", "100 Focus required").
- **Competency levels are evidence, not progress.** `none < introduced < developing < demonstrated`: a completed lesson or a guided pass only ever makes a skill *introduced*; *developing* needs an independent pass; *demonstrated* needs the skill's full requirements (varied independent passes). XP, levels, quests and lesson counts never enter the graph.
- **Real runtimes for every technology.** Python/SQL (Pyodide), Web (Chromium sandbox), **R (real R in webR, a fresh environment per check)**, **spreadsheets (an in-house formula/pivot/chart engine graded by recomputing the workbook on hidden data)**, **Git (a simulator that replays the player's command transcript and grades the repository STATE, never the commands)**. Grade by behaviour and state; accept every valid implementation.
- **Hidden data everywhere.** Spreadsheet checks use `with` overrides (other figures, other thresholds, other tables); R/Python checks run the program on different files or crafted databases built inside the check; Git checks grade the final repository. Helper code shipped in a check must be **namespaced** (`_rf_*`) so it can never overwrite a name in the player's program (this was a real bug: a reference helper silently replaced the player's).
- **Every wrong attempt is a test, for every language.** Solutions live in test-only files per language (`*/solutions*.testdata.ts`, plain Node, no imports; Python and R written with `String.raw`). When a wrong attempt passes, strengthen the DATA (boundary values, ties, unknown/NULL rows, negative relationships, idle groups), not the wrong attempt: several datasets in this phase were rebuilt that way.
- **Statistics is taught honestly.** Denominators (n vs n − 1), missing values, uncertainty, "no clear difference" as a finding, charts that do not mislead. Numbers are computed from the stated method (quartiles by the median-of-halves rule, nearest-rank percentiles); the brief says which.
- **Dailies draw from everything the player has been taught.** `game/dailySelect.ts`: current / review / **mixed** (cross-world or transfer) rotate; the pool is every non-guided challenge whose skills are introduced, in any world. A daily is optional, one attempt, no hints, **never costs Focus**, never a remediation; it needs Focus 100 to attempt like everything else. Dailies are evidence, never mastery.
- **Review is scheduled from the record.** `game/retention.ts` `reviewSchedule`: intervals grow with consecutive independent hint-free passes (2, 7, 14, 30, 60 days), shrink after a failure or a hinted pass (next day), and every due review says why. Nothing is scored; being due never lowers a status.
- **Training is global.** A failure in any world makes a small plan from content the player has been taught (any world), in different contexts from the exposing problem; depth follows the failure level (`game/focus.ts`). Refresher cards for every skill are authored (`content/training/notes.pro.ts`). Balance lives in one table (`game/balance.ts` + the modules it gathers) with a test that keeps it coherent.
- **The Summit is open-ended and multi-technology, and still finite.** `BossDef.requiresAnyOf` (any three mastery guardians) and `BossDef.routes` (the finale in a technology the player has mastered: Python+SQL, analytics, spreadsheets, R). A retry is always a NEW version in the route chosen; winning by any route ends the campaign.
- **The learning engine knows nothing about graphics.** Worlds are a *reaction* to demonstrated work: `Challenge.worldEffects` → a `worldEffect` event on the first pass → `deriveWorldState(save)` rebuilt from evidence (`game/worldEvents.ts`, `content/worldEffects.ts`). A future scene (robot yard, original wizard academy, API district, racing) maps targets to its own objects; it adds no rule, no challenge and no saved data. Do not build Phase 6 here.
- **Independent and boss briefs name no tools.** Checked by tests for spreadsheets (no function names in the brief) and R (no R function names); Field Manual entries document what was never taught and every example is executed (`reference.pro.test.ts`: R in webR, formulas in the engine, Git in the simulator, Python in Pyodide).

## Educational design rules added in Phase 6 (keep them)
- **The 3D world is a presentation of the learning engine, never a second one.** Scenes are data (`content/play/`); logic is pure (`play/logic/`); three.js lives only in `play/engine/` and loads lazily. World state is `deriveWorldState(save)` (never stored); the only 3D save data is `save.play` (position, talked/seen, settings). No scene may add a rule, challenge or authority over XP, Focus, evidence or quests.
- **Terminals open the real lesson screen**; failure still costs Focus and requires training in the Simulation Room (the Training Grounds, in-world), returning to the exact lesson. No in-world shortcut, shop item, hint seller or "retry" exists. The Daily stays optional/one attempt/no hints/no Focus cost; progress in the world is never labelled skill.
- **Never put gameplay on the main thread that needs `eval`**, and keep world-only helpers (`__cq3d`) gated behind `localStorage codequest.e2e`.
- **Performance is a requirement**: share geometries/materials, dispose on scene change, memoize per-save derivations, keep heavy chunks (three.js, editor, runtimes) out of startup. Re-measure (`scripts/perf-probe.mjs`) after touching `game/graph.ts`, `content/index.ts` or startup imports.
- **No runtime import cycles in `src/play`** (a test enforces it): they only fail on the unbundled dev server, which the built-app e2e does not exercise. `e2e/dev3d.mjs` starts the world on the dev server too.
- **Stay original**: the fantasy academy borrows nothing from any existing franchise.
- Phase 6 is the last planned phase; do not start another without being asked.

## Educational design rules added in the Phase 6 finishing pass (keep them)
- **A world reaction is the reward for a pass, never an errand.** The first independent pass that changes the world plays its reaction at once over the lesson and hands the lesson back. A failure is never acted out in the world (no malfunction cutscene); Focus and training are the only consequence. Do not add buttons, NPC steps or "go and talk to" gates between a pass and the next lesson.
- **Guidance is derived, never scripted.** The objective comes from `objectiveFor(save, scene)`: the plaza never names a lesson; a world names its own next step from the learning record (training, due review, next open lesson, story activity). Never hard-code a lesson order in the 3D layer and never add a second source of "where do I go" (markers, trail and HUD all read the same objective).
- **Collision comes from what is drawn.** New props get colliders from their meshes (`engine/collide.ts`), not from hand-typed sizes. After dressing a scene run `node scripts/integrity3d.mjs` and fix what it reports (walk-through, floating, spawn or NPC inside a solid) rather than adding invisible boxes. Ring-shaped props need explicit wall chains.
- **Machines are planned, not tweened**: use `armMotion.ts` (joint S-curves, limits, holds) for anything articulated, and let a cinematic `await` the machine.
- **Cinematics are short and earned**: a pass answers in a few seconds, only milestones get longer sheets (`cinematics.test.ts` caps a sheet at 11.5 s), a level-up is a banner.

## Educational design rules added in Phase 6 polish pass 3 (keep them)
- **Nothing in the world ever hides because the player is near it.** The camera is a spring arm (`engine/stage.ts updateCamera`): walls, tall furniture and tree crowns between the character and the wanted camera position shorten the arm. Never reintroduce occluder hiding (it made trees, walls and machines vanish up close). `node scripts/visaudit.mjs` walks the player to every collider edge and fails if a prop is hidden or culled; run it after dressing a scene.
- **A cutaway shows what a pass means somewhere else, and only after a pass** (`content/play/cutaways.ts`, `SceneDef.reactions[].then`, `PlayScreen startCutaway/endCutaway`). A failed attempt produces no `worldEffect`, so it can never play one. The sheet is an ordinary skippable cinematic (< 11.5 s); the player is faded to the place, shown the sequence and returned to exactly where they stood with the lesson open. A cutaway changes no learning state. The baseball plays are real plate appearances from `engine/ballplay.ts` (the simulated game uses the same engine); the racing runs are real sections of the replay lap with the player's setup.
- **Training arrival is automatic.** Arriving in the Simulation Room for owed training plays a short scene chosen by the weakness's skill family (`play/logic/trainingKind.ts`), then opens the console with no click in between.
- **The Pack is gear, never an advantage.** Cosmetics are worn in slots (`save.play.gear`, save v10) and change the avatar in the 3D world; the Pack, the avatar and the shop read the same item data. **Focus bars were considered and declined:** the only way Focus returns is by completing a required training plan, and a bar that is useful (that lets a player skip part of a plan) is exactly the shortcut this file forbids; a bar that is not useful would be a fake item. Nothing sold may give XP, Focus, hints, answers or evidence.
- **The source-data viewer shows only a lesson's own visible data** (`learning/sourceData.ts`, `app/components/DataViewer.tsx`): its databases (tables, columns, links read from the schema notes, sample rows from the same setup SQL), its fixture files (CSV as a table, JSON formatted) and the practice API's visible data set. Hidden twins (`-b`, `-boss`, `-edge`) and internal files are never offered.
- **NPC remarks read the real record and only point** (`content/play/hints.ts`, `play/logic/hints.ts`): strong/begun/untouched/trouble per world come from evidence and open weaknesses, never XP or levels; a remark names a place, a world or the Training Grounds, never how to solve anything, and is said once.
- **The Quest Journal is a view, not a progression** (`game/journal.ts`): it groups the existing quests, lessons, skills and evidence by world; it adds no rule and no state.

## Educational design rules added in the Phase 6 final polish pass (keep them)
- **The rig's arm axes are fixed by the skeleton, not by taste.** The shoulder joints hang from the torso at x = ∓0.225; a NEGATIVE x rotation swings a limb forward (and flexes an elbow), and for `upperL` a NEGATIVE z rotation swings the arm away from the body (positive tucks it into the torso: that sign mistake made every arm clip the chest). Locomotion is one parameterised function in `engine/rig.ts` (swing, elbow flex, abduction, landing, idle hand); a gesture is a controlled override blended over it, never a second skeleton. `scripts/armlab.mjs` renders any motion from front, three-quarter, side and back: use it for every rig change.
- **The plaza is a hub, not a menu.** `engine/builders.hub.ts` holds its pieces; the floor is ONE painted plane, the gatehouses are built from a handful of materials (batched), only the core animates. Keep the plaza's draw calls below the busiest scenes (it measures ~150) and its textures to the single floor and the title boards.
- **A lap starts when the car crosses the start/finish line, never because time passed or the car moved** (`play/logic/lapTimer.ts`: directional segment crossing of the track's own first point, across the asphalt only; a lap needs every checkpoint in order; backing over the line counts for nothing). Reverse is a driver request (`Driving.reverse`, the S key), a slow heavy gear that engages only from a near-standstill; the lap-time AI and the replay never reverse.

## Focus rules (keep them)
- **100 Focus = ready to attempt; below 100 = train first.** Enforced in the game layer (`submitChallenge`, `submitBoss`, `submitDaily`, `revealHint` refuse below 100), never only in the UI. There is **no Rest, no Focus item and no other shortcut**: Focus is earned back only by completing steps of a required training plan (`game/focus.ts`). Never add a way to restore Focus outside training; never let Focus exceed 100.
- **Failure levels are data** (`FAILURE_LEVELS`, `HINTED_PASS_LOSS`, `STEP_WEIGHT` in `game/focus.ts`): 1 small task, 2 difficult task, 3 independent challenge, 4 mini-boss, 5 mastery boss/Summit. Guided (learning-mode) exercises and Practice Yard attempts cost nothing. A required plan's steps share exactly the Focus that was lost (the last step, the proof, takes the remainder), so the plan is sized to the Focus needed and ends at 100.
- **Language**: say "Not ready" and "100 Focus required", never "locked", for the Focus gate.
- **Retry is a new variant** after the return; the return point is the exact challenge (or boss).

## Development guidelines
- Stack: Vite + TypeScript (strict) + Preact + CodeMirror 6 + Pyodide + Vitest (+ playwright-core for e2e). See ARCHITECTURE.md.
- Commands: `npm run dev`, `npm run typecheck`, `npm test`, `npm run build`, `npm run e2e` (builds, generates `e2e/.fixtures.json`, serves, drives real Chromium; `E2E_ONLY=<substring>` runs matching tests only, e.g. `E2E_ONLY=Daily node e2e/run.mjs` against an existing build). All of typecheck, test, build and e2e should pass before finishing a phase. Web content tests need a Chromium (`CHROMIUM_PATH`, or `/opt/pw-browsers`); run one challenge with `npx vitest run src/content/web -t "<challenge id>"`.
- `npm install` runs `scripts/copy-pyodide.mjs` (copies the Python runtime into gitignored `public/pyodide/`) and `scripts/copy-webr.mjs` (the R runtime into gitignored `public/webr/`). If Python or R fails to load in dev, run the matching script. R content tests (`src/content/r`, `src/content/boss/boss.r.test.ts`) run real R in Node and take a few minutes.
- Game rules go in `src/game/` as **pure functions** returning `{ save, events }`; UI never mutates saves. Curriculum goes in `src/content/` as data. Learning-engine code goes in `src/learning/`.
- Save data is versioned (`src/core/save.ts`). Any change to saved shape MUST bump `SAVE_VERSION` and add a migration so existing player progress is never lost; add a migration test.
- Adding a lesson: new file in `src/content/<area>/`, register in `src/content/index.ts`, add reference solutions **and wrong attempts** to `solutions.testdata.ts`; `npm test` validates it in real Python. Update quest objectives/unlock rules in `content/world.ts` if needed.
- Adding a SQL/data lesson: files in `src/content/sql/` or `src/content/dataeng/`, register in `content/index.ts`, add solutions to `sql/solutions.testdata.ts` or `python/solutions.phase2.testdata.ts`, and add any new database (plus its `-b` hidden twin) to `content/databases/`.
- Adding a web lesson: `src/content/web/NN-*.ts` (see `docs/WEB_SANDBOX.md`), register in `content/index.ts`, reference solutions AND wrong attempts in `content/web/solutions*.ts`. Adding a Daily: `content/daily/` (+ `solutions*.testdata.ts`). Attaching extra variants to an old lesson: `content/python/variants-phase3.ts` (appended by `content/index.ts`).
- Adding a boss: `content/boss/<track>.ts` (versions built with `bossChallenge`, all checks hidden), a definition in `content/bosses.ts` (lessons/bosses required, story text, reward), solutions in `content/boss/solutions*.testdata.ts`; `content/boss/boss.test.ts` and the web tests validate it.
- Adding a language: a new `CodeRunner` in `src/learning/<lang>/` (see `runner.ts`) and a branch in `learning/gradeAny.ts`; do not special-case the UI beyond the editor/workbench for it.
- Adding a spreadsheet lesson: `src/content/sheet/NN-*.ts` (workbook data + `cells`/`isFormula`/`pivot`/`chart` checks with hidden `with` data), register in `content/index.ts`, reference workbook edits AND wrong attempts in `content/sheet/solutions.testdata.ts`; `npx vitest run src/content/sheet` validates. Adding a Git lesson: `src/content/git/NN-*.ts` (a `RepoSnapshot` start + state checks), solutions in `git/solutions.testdata.ts`. Adding an R lesson: `src/content/r/NN-*.ts` (function checks via `rCalls`, output checks via `rOut`), solutions in `r/solutions.testdata.ts`. Adding a statistics lesson: `src/content/stats/NN-*.ts` with `statCalls` (computed reference, never typed expectations), solutions in `stats/solutions.testdata.ts`.
- A new lesson whose skills cross worlds declares `requires: [{ skill }]` (never a prerequisite on a lesson of another world); a new world is one entry in `content/worlds.ts` plus its area in `content/world.ts`.
- Adding a boss route: versions in `content/boss/`, a `BossRoute` in `content/bosses.ts` (`needs` = the mastery guardians that open it), solutions in the matching `solutions*.testdata.ts`.
- Add tests for logic. Keep e2e for behaviour that only a real browser can prove.
- Match surrounding style; comments explain *why*. Keep dependencies few and justify new ones in ARCHITECTURE.md.
- At the end of every work session update `PROGRESS.md` (completed / incomplete / known issues) and `ARCHITECTURE.md` if structure changed. Document significant schema changes.
- Work on the branch the session instructs; don't open or merge PRs unless asked.
- Only proceed into a new phase when the user asks. Do not pre-build later phases' content.
