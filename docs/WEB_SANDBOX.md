# The web sandbox and the in-game API: design and security model

Player HTML/CSS/JavaScript is untrusted code. Phase 3 runs it in a **sandboxed iframe** that the game controls, and grades it in a **real browser** (Chromium in tests, the player's own browser in the game) rather than in a DOM emulator, so layout, computed styles, forms, focus and timing behave exactly as they do for real pages.

## Architecture
```
Game page (trusted)                         web-sandbox.html  (separate document, own CSP)
 WebRunner.ts ──creates iframe sandbox="allow-scripts"──►  sandboxRuntime.js  ── document.write(player HTML + prelude)
        ▲                                     │   (opaque origin: no allow-same-origin)         │
        └── postMessage protocol (hello/nonce, ready, console, error, request, result) ◄────────┘
```
- `web-sandbox.html` is generated by `sandboxPage.ts` from `sandboxRuntime.js` + `apiServer.js`; Vite serves it in dev and emits it in the build (`vite.config.ts`). It has its own strict CSP (no network: `connect-src 'none'`, no frames, no forms), separate from the game page's CSP.
- The iframe has `sandbox="allow-scripts"` and **no `allow-same-origin`**: the page runs in an **opaque origin**. It cannot read the parent DOM, `localStorage`, cookies, IndexedDB or the game save. `window.origin` is `"null"`.
- Runtime lockdown (before the player's code): `fetch` is replaced by the in-game API client; `XMLHttpRequest` throws; `localStorage`/`sessionStorage` are private in-memory shims (each run starts empty or with the check's seed); `alert/confirm/prompt/window.open` are recorded, not shown.
- Protocol: the sandbox sends `hello` with a random **nonce**; the host answers with the files and config and accepts later messages only if they carry that nonce (and come from the iframe's window). All incoming data is capped in size and treated as untrusted text. The host renders it with Preact text nodes, never `innerHTML`.
- **Grading** (`mode: 'grade'`): a fresh iframe per check. After the page loads, the authored check script (an async function body with helper `h`) runs *inside* the sandbox against the live DOM (`h.click/type/select/submit/press`, `h.style/rect`, `h.tick/settle`, `h.api`, `h.storage`, `h.logs`). Timers run on a **virtual clock** in grade mode, so a "wait 30 seconds" behaviour is checked instantly and deterministically.
- **The same page and protocol** are driven by Playwright in Node for content validation (`learning/web/testHarness.ts`), so every shipped web challenge is proven in real Chromium: starter fails, valid solutions pass, wrong attempts fail.

## Honest limits
- A determined player can forge results (the check runs in the same document as their code) or edit their own save. Single-player learning tool: the same stance as the Python worker. Do not build server-trusted or competitive features on this without server-side grading.
- The sandbox stops the page reaching the game and the network; it does not stop the page burning CPU. An endless loop in player code freezes only the sandboxed iframe (measured in Chromium: the game page stays responsive, covered by an e2e test); the host aborts grading after 8 s, reports "the check did not finish in time" once (not once per check) and tears the iframe down on Run/Reset/navigation. A hang is still a failed submission, like any other.
- Images inside the page can only be `data:` URIs (CSP), so a page cannot phone home through an `<img>`.
- Browsers differ slightly (fonts, default styles). Checks measure structure, computed styles and geometry with small tolerances rather than pixels.

## The in-game API (`apiServer.js`, `apiData.ts`)
A deterministic, in-memory REST/JSON service behind `fetch`. It never touches the network.
- Collections (`machines, teams, players, products, employees, weather, races, measurements, courses`) come from a seeded generator, in a visible data set **a** and a hidden twin **b** (same shape, different rows; so hard-coding what the example returns fails). A few boundary values are deliberate (stock 0/9/10, tied league records, a one-seat course).
- Reads: `GET /api/<c>`, filters `?field=value`, `?q=` (name search), `?sort=field|-field`, `?limit&offset`, header `X-Total-Count`. `GET /api/<c>/<id>` or 404.
- Writes: `POST` (JSON body, `Content-Type: application/json` or 415; missing fields 400; 201 + `Location`), `PUT`/`PATCH`, `DELETE` (204, no body). 404/405 are proper answers.
- Auth: `GET /api/private/<c>` needs `Authorization: Bearer codequest-key` else 401.
- Failure modes for error-handling lessons: `/api/flaky` (503, 503, then 200), `/api/rate-limited` (200 ×3 then 429 with `Retry-After`; the value differs in the hidden set), `/api/slow` (400 ms), and a check-only `h.api.failNext(n, status)` that forces the next `n` responses to fail.
- Latency is simulated with the (virtual) clock. Every request is recorded (`h.api.calls`) and shown to the player under the preview as a network log.
- The server is documented in the Field Manual (`web-api-ingame`, `web-http`, `web-fetch`): documentation is practice, and independent challenges may need entries never taught.

## Adding web content
1. A lesson file in `src/content/web/NN-*.ts` (uses `wc`, `web`, `webDemo`, `jsCalls` from `web/helpers.ts`); register in `content/index.ts`.
2. Reference solutions AND wrong attempts (one deliberate mistake each) in `web/solutions*.ts` (test-only). `npx vitest run src/content/web -t "<challenge id>"` runs them in Chromium.
3. Checks assert behaviour/structure/geometry, never source text. If a "wrong" attempt passes, the check is weak: change the check (or the data) so it distinguishes them, or drop the attempt if it is genuinely equivalent.
4. Independent challenges: blank or skeleton files, no hints/concepts/constraints, every check hidden, contexts the player has not seen, and a hidden API data set where an API is involved.
